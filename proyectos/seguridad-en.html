Security

An app that runs on your own computer still has someone on the other side. I reviewed it before opening the beta.

02

Scope

Cathedra runs on the student's computer: a desktop window talks to its own HTTP server, which reads and writes their lectures, transcripts and notes.

That design is deceptive. Because the server only listens on the machine itself, it feels like nobody is on the other side. Someone is: any page open in another browser tab can send it requests.

Before releasing the installer I wanted to know what could go wrong, what it would cost and what to fix first. I reviewed the local server, the accounts, the admin panel, how the installer is published and which data leaves the machine.

03

Threat model

Six actors, what each one wants and how they would get in. Each one maps to risks in the next table.

  • A page from another site

    What they want
    To make the app open a program, delete files or hand over transcripts.
    Way in
    Requests to the local server from another tab, or from a domain that resolves to the machine itself (DNS rebinding).

    Risks: R1R3

  • A crafted input

    What they want
    To escape the study folder and read or run another file on disk.
    Way in
    Lecture, subject or topic names that arrive in the request address.

    Risks: R2

  • Someone holding the disk

    What they want
    Passwords, sessions or the user's AI service key.
    Way in
    A shared computer, a backup, a copied file.

    Risks: R4R6

  • Someone guessing passwords or codes

    What they want
    To get into an account or the beta without permission.
    Way in
    The sign-in screen and the beta access codes.

    Risks: R5R8

  • Me, by mistake

    What they want
    Nothing; the risk is publishing a key or a personal path inside the package.
    Way in
    The installer and the modules uploaded to a public repository.

    Risks: R7

  • Someone handing out a fake installer

    What they want
    For someone to run their modified version.
    Way in
    An unsigned installer: Windows warns the same way for the original and for the copy.

    Risks: R9

05

Findings and decisions

The three that weighed most, with what I ruled out. Below, the rest of the defenses in one line each.

01
What I saw

The server only listens on the machine itself. That hides it from the network, not from the student's browser: a page from another site can send it requests, and even if the browser hides the response, the effect still happens.

I decided

Reject every API request whose Origin is not the machine itself, on reads and on everything that changes something.

I ruled out

Trusting that it only listens on the machine itself.

Because That was enough for another tab to make the app open a program or delete files.

02
What I saw

Comparing paths as text does not stop “..”: a path that seemed to fall inside the study folder ended up, once resolved, at a system executable.

I decided

A bare name is accepted only if it fits a strict alphabet; a full path is resolved before checking that it falls inside.

I ruled out

Sanitizing the input by removing the “..” and moving on.

Because Sanitizing is a losing game: there is always one more encoding. Slashes, “..”, drive letters, control characters, ambiguous Unicode and Windows reserved names are rejected.

03
What I saw

The installer and modules are uploaded to a public repository, and a key or a personal path can slip into any text file.

I decided

A guard inside the publish command that stops everything if it finds keys, credentials or personal paths.

I ruled out

Checking by hand before each release.

Because A manual check gets skipped on the day you are in a hurry. The guard always scans everything about to be uploaded, before the installer is built.

The other defenses

  • Passwords with scrypt and salt

    What is stored is scrypt(password, salt), never the password; for sessions, only their SHA-256 fingerprint. Holding the file gets you into nothing.

  • Attempt limit

    Five failed attempts per email within five minutes and it locks. Without that, an eight-letter password falls in an afternoon.

  • Atomic writes

    Every file is written whole or not at all: a temporary file next to it, then a one-step replace.

  • Beta codes as fingerprints

    Only their fingerprint is stored, compared in constant time, and each code has a per-minute request limit.

  • The user's key, encrypted

    The key to their AI service is stored encrypted with Windows data protection (DPAPI), bound to their account.

  • A panel with three locks

    Only on the machine itself, it rejects proxy or tunnel headers, requires its own Host and asks for a per-session secret. It sends CSP, X-Frame-Options and Referrer-Policy.

  • The interface does not reveal how it is built

    Messages the person sees never name files, fingerprints or internals; a test checks it.

  • What ships is what was built

    Publishing compares SHA-256 fingerprints: if anything changed after the build, it does not upload.

The same checklist, in another app

In Fortal, my training app, the server only fetches over https from a fixed list of sites, follows redirects by hand (two at most) without leaving that list, with a time limit and a byte cap: no SSRF. Incoming bodies have a cap per route, and a sweep of 15 routes checks they answer 401 without a credential and 403 with someone else's. Twelve tests cover it.

07 — Result

The five high-priority risks dropped to medium or low.

With the defenses in place and 126 security tests passing. It is my own review: nobody from outside has audited it yet.

Residual risk and what I would do next

  • 01

    DNS rebinding on reads

    The panel requires its own Host; the app server still relies on the Origin check. Next step: the same Host allowlist on all its routes, with its test.

  • 02

    CSP in the main window

    Today the panel sends it. Bringing it to the app window comes right after the Host check.

  • 03

    The DPAPI limit

    It protects against another Windows account or a copied disk, not against malware running under the same account. Accepted: it is the ceiling for a desktop app without dedicated hardware.

  • 04

    Unsigned installer

    Windows shows its warning; the download page explains it and every release publishes its SHA-256 fingerprints. Accepted for a small beta; sign it before opening it wider.

  • 05

    Signed licenses

    Signing licenses with Ed25519 is planned, not done.

  • 06

    External audit

    I would get one before charging: your own review finds what you already know how to look for.

08

Legal and privacy before the beta

I researched the law at its official source before releasing the beta. This is general information, not legal advice: anything uncertain was flagged for a lawyer to confirm.

  • 01

    Which data travels

    Audio is transcribed on the computer. With the local engine nothing leaves; with the cloud engine, the question and the pieces of material needed to answer it travel. The admin usage log stores counts, never content.

  • 02

    Consent

    Argentina's Law 25.326 (art. 5) requires free, express and informed consent to process personal data, and it can be withdrawn.

  • 03

    International transfer

    Art. 12 restricts sending data to countries without adequate protection, and the United States is not on the data authority's list. That is why cloud mode asks for express consent and a local alternative exists.

  • 04

    Recording lectures

    The Civil and Commercial Code (art. 53) requires consent to capture a person's voice, with an educational exception; Law 11.723 (art. 27) bars publishing lectures without authorization. Recording depends on each course, and a recording is not published.

  • 05

    AI notice

    Every answer cites the lecture, the minute and who said it; what is not in the material is marked as missing instead of being made up.

  • 06

    Terms and consumer law

    Terms and privacy drafted for the beta. If it charges, Law 24.240 and Provision 954/2025 require visible withdrawal and cancel buttons, and cancelling through the same channel.

09

Short review of the portfolio demos

I applied the same checklist, on a small scale, to the two brand demos on this site: the 3D configurator and the catalog assistant. I reviewed the 4 Nov 2026 version; on 10 Nov 2026 the policy was applied across the whole site.

  • Minimal surface

    Static same-origin files: no server, no cookies, no analytics and no forms that send data. The assistant's catalog is a local file and the question never leaves the browser.

  • No third-party scripts

    three.js and the fonts are served from the site itself. The only outside references are links to the sources of the figures, with rel="noopener noreferrer", and no page sends its address as referrer ("no-referrer").

  • User input

    The assistant's field is capped at 240 characters and what you type goes in as text or escaped: it is never interpreted as HTML. In the configurator, HTML is only built from its own data.

  • Licensed assets

    CC0 and CC BY 4.0 3D models and CC0 HDRI environments, credited in the demo footer and on the Credits page.

  • Finding

    The configurator set each swatch color with a style attribute, which a strict policy blocks. Fixed: it now sets it with style.setProperty, and no page on the site uses inline style attributes or inline event handlers.

  • Hosting limit

    The site is published on GitHub Pages, which does not allow custom headers: the CSP goes in a meta tag, where frame-ancestors does not work. Low risk: a demo with no data has nothing to steal inside an iframe.

Policy applied to the configurator

default-src 'none';
script-src 'self' 'sha256-…' 'sha256-…';
style-src 'self';
img-src 'self' data: blob:;
font-src 'self';
connect-src 'self' blob:;
media-src 'self';
manifest-src 'self';
object-src 'none';
base-uri 'none';
form-action 'none'

Every page on the site applies its own: a meta tag with the SHA-256 fingerprints of each inline script and style, recalculated by a script in the repository. An automated test fails if a fingerprint does not match and visits every page in the browser looking for policy violations and console errors. To report an issue: /.well-known/security.txt.

10

How I did it with AI agents

  1. The threat written into the brief.

    Every sensitive module opens by explaining what it protects and why: “what is protected, because it is what gets stolen”. That explanation was the batch's acceptance criterion.

  2. One defense, one test that attacks it.

    Foreign origins, paths with “..”, five bad passwords, a key planted in the package: every defense came in with the test that tries to break it.

  3. Measure instead of assuming.

    That comparing paths as text is not enough was shown with a case that passed validation and ended at a system executable. That case is now a test.

  4. What I redid.

    The first version of the Origin check required the exact port. The desktop window starts its own server and the port stayed at zero: every request that changes something returned 403, in 19 places, and on screen it looked like buttons that did nothing. I changed it to accept any port on the machine itself, which is what matters to stop: a page from the internet.

  5. Run everything again at the end.

    To write this case I ran the four security suites again: 126 passing and 4 skipped.

What I would change

I would write the threat model on day one. The defenses arrived module by module, which is why the Host check ended up in the panel and not in the app server. A single checklist from the start would have avoided it.

Still missing: an outside audit and a signed installer before opening the beta to more people.
